# M4 Launcher and Process Truth — Arc Plan

> **Pre-approval arc plan.** ROADMAP prescribes a 1–2 page plan with approval before source for
> this arc. This is the decision document for maintainer review, not an execution plan; the
> task-by-task implementation plan (steps, code, checkboxes) follows approval.

**Goal:** Deliver M4: a public `OpenCodeServer.StartAsync` launcher in core `OpenCode.Sdk` —
start, JSON readiness probe, stop/dispose with bounded tree termination (ADR-0001); the
test-only `PinnedOpenCodeServerFixture` (TUnit, `SharedType.PerTestSession`, initially over a
test-only CliWrap adapter per design §7.2); the repository-owned C# WebSocket JSON-RPC drive
controller in `tests/Shared`; and the blocking deterministic simulated-model session workflow
test (§7.4, ADR-0022). Demo: the SDK starts the server itself and calls health. Three-OS
acceptance.

**Architecture:** The launcher is hand-rolled on `System.Diagnostics.Process` — no process
library in the product (ADR-0001; repo tests may use CliWrap). It spawns `serve --stdio --port 0`
with a caller-generated `OPENCODE_PASSWORD` injected through the child environment, drains both
output streams continuously, parses the single JSON stdout readiness line for the endpoint, holds
stdin open as the ownership lease, and tears down stdin-EOF → bounded grace → forced tree kill.
The fixture is a control adapter that separates launcher failures from SDK/server agreement;
launcher-focused integration tests dogfood the production type (§7.3). The workflow test runs the
pinned server from source in simulation mode and scripts provider chunks through the drive
backend's WebSocket JSON-RPC channel via a small C# controller beside the assertions.

**Tech Stack:** .NET multi-TFM (net472/netstandard2.0/net8/net9/net10) for the launcher; TUnit on
Microsoft.Testing.Platform; CliWrap (test-only); `ClientWebSocket` for the drive controller; bun
source-run of `external/opencode` as the server under test.

**Spec:** design doc §7.1–7.4 and §10
(`docs/superpowers/specs/2026-08-26-continuous-protocol-coverage-program-design.md`), ADR-0001,
ADR-0022, research log Q148 — re-verified below at the current pin.

## Process-truth facts the arc argues from (Q148, re-verified at pin `d2ee536c`, 2026-08-28)

- `serve --stdio --port 0` is the reference client's exact argv
  (`packages/cli/src/services/standalone.ts:21`); the serve command accepts `--stdio`
  (`packages/cli/src/commands/handlers/serve.ts:9`).
- Readiness is one JSON stdout line `{"url":…}` printed only after full boot
  (`packages/cli/src/server-process.ts:163`); the reference keeps draining stdout afterward.
- stdio mode never prints the password (the foreground-only print at `server-process.ts:164`)
  and scrubs `OPENCODE_PASSWORD`/`OPENCODE_SERVER_PASSWORD` from the env copy
  (`server-process.ts:69–71`); the caller injects the lease credential at spawn
  (`standalone.ts:25`).
- stdin EOF ends the scoped server lifetime (`server-process.ts:168–170`, `waitForStdinClose`
  at `:199`).
- Reference teardown: SIGTERM, 3-second force-kill (`standalone.ts:31–32`); Windows group kill
  is `taskkill /pid <pid> /T /F` (`packages/util/src/cross-spawn-spawner.ts:299`).
- Simulation gating: `OPENCODE_SIMULATE` truthy (`server-process.ts:93`) plus `OPENCODE_DRIVE`
  set (`packages/simulation/src/backend/index.ts:32`) plus a provider block via
  `OPENCODE_CONFIG_CONTENT` (`server-process.ts:113`); the JSON-RPC methods `llm.request`,
  `llm.chunk`, `llm.disconnect` exist (`packages/simulation/src/backend/simulated-provider.ts:334,349,353`).
- **Refinement found (not drift):** `OPENCODE_DRIVE` is an instance *name*, not a flag. `=1`
  selects built-in fixed ports `ws://127.0.0.1:40900/40950`; any other name reads
  `$DRIVE_REGISTRY_DIR/<name>.json` (`packages/simulation/src/manifest.ts:70–77`) — so the
  fixture must use a named instance with a per-run manifest to stay parallel-safe. The
  controller protocol also requires `simulation.handshake` + `llm.attach` before requests flow,
  and offers `llm.finish`/`llm.pending` (`simulated-provider.ts:311–355`).

## Decisions the maintainer must confirm

- **Public API shape — resolved (maintainer, 2026-08-28):**
  `OpenCodeServer.StartAsync(OpenCodeServerOptions, CancellationToken)` returning the started
  server as an `IAsyncDisposable` working object (endpoint, credential, `CreateClient()`),
  mocking convention applied — this grows the PublicApi baseline. `CreateClient` pins identity
  **fail-closed**: `OpenCodeClientOptions` carries exactly four members today (`Endpoint`,
  `Username`, `Password`, `Location`) — the first three are identity and belong to the door;
  the configure delegate receives an options instance with identity unset, and if the caller
  sets any of the three the door **refuses** with `InvalidOperationException` (the established
  conflicting-BaseAddress-refuses posture) before writing its own endpoint/credential and
  building the client. `Location` (and any future behavior knob, e.g. the M6-deferred timeout)
  stays freely configurable. Per-call `OpenCodeRequestOptions` carries only
  `ErrorBehavior`/`Location` — no endpoint or auth channel exists there, so no per-request
  escape hatch. Each `CreateClient` call creates a new client owning its transport; the caller
  disposes it.
- **Server doors — full upstream parity, upstream vocabulary, structural ownership (maintainer
  direction 2026-08-28):** the SDK targets all three upstream connection modes, named after
  upstream's own verbs — no invented method names, variations ride options arguments:
  1. **Standalone start** (`Standalone.start`, `packages/cli/src/services/standalone.ts`; CLI
     `--standalone`) → `OpenCodeServer.StartAsync`: always a fresh private server on port 0 with
     its own generated credential and stdin lease; never discovers or attaches; coexistence with
     any running server is safe by construction. The returned working object is the **only owning
     type**: disposal ends exactly its own child (the lease does it even on owner crash).
  2. **Explicit endpoint** (CLI `--server`; upstream builds a plain client plus a 5s-timeout
     health check and a version warning, `server-connection.ts`) → plain `OpenCodeClient`
     construction; the health/version validation lands as an option on client or a small helper,
     not a new verb — "attach" is not upstream vocabulary and is not ours either. No stop door
     exists on this path, structurally.
  3. **Background service** (`Service.discover/ensure/stop`, public export
     `@opencode-ai/client/service`, `packages/client/src/promise/service.ts:255`) →
     `OpenCodeService.DiscoverAsync/EnsureAsync/StopAsync` with options mirroring
     `DiscoverOptions` (registration `file`, `version` gate), `EnsureOptions` (+ `command`
     defaulting to `opencode serve --service`, `env`, `onStart`), `StopOptions`. Discover and
     ensure return **non-owning endpoints** (no kill switch on the result); stopping the
     registered daemon is only the explicit `StopAsync` act, mirroring upstream's separation.
  **This arc lands door 1 (and door 2's validation option); doors 3's ensure/stop split into
  their own follow-up arc** — the contender/backoff/version-replacement/PTY-handoff machinery is
  a full arc of work, and the registration file + `--service` flavor are upstream-observed
  contracts outside the OpenAPI pin (ADR-0013 provenance; drift guarded only by the canary).
  Read-only `DiscoverAsync` rides the follow-up arc, not M4 (resolved, maintainer 2026-08-28):
  its contract is the registration
  file — the follow-up arc's core — and testing it honestly needs the `serve --service` daemon
  flavor or synthetic registration files, machinery that arc builds anyway; M4 already carries
  the fixture, controller, and workflow test.
- **TFM scope — resolved (maintainer, 2026-08-28):** launcher on all four TFMs from day one;
  the net472 stdout-drain and tree-kill items stay named task work inside Tasks 1–2, never a
  deferral. Downlevel gap-closing order (standing maintainer rule): first check whether
  Polyfill already supplies the missing capability, then the official Microsoft downlevel
  packages (the established `System.Memory`/`Microsoft.Bcl.*` pattern from the runtime arc),
  and hand-roll only when neither covers it.
- **Server under test in CI — resolved (maintainer, 2026-08-28):** bun source-run from the
  pinned submodule on all three OS runners (`bun install --frozen-lockfile --ignore-scripts`);
  the simulation package exists only in bun/source-run builds. The cost is accepted; the runs
  must stay deterministic (frozen lockfile at the pinned commit) and cached — bun install
  keyed on the lockfile hash per OS.
- **Gating window — resolved (maintainer, 2026-08-28):** the workflow test is CI-blocking from
  day one, as ADR-0022 already requires; a flake never loosens the gate — it is fixed as a bug,
  and the fixture is engineered fail-fast so a hang cannot masquerade as coverage.

## Noted for later (outside this arc)

- **Extensions launcher lifecycle:** `AddOpenCodeServer` + hosted-lifecycle DI is deliberately
  not in M4 — a singleton client resolved by constructor injection races a server whose endpoint
  exists only after `StartAsync`, and solving that (deferred endpoint, lazy factories) would cut
  against ADR-0010's simplicity-first construction without a real consumer. Trigger: this repo's
  MCP server arc (the expected first owner of a launcher lifecycle) or the first concrete
  external ask — the A6 open-question pattern. Until then the Generic Host recipe is: inject
  `OpenCodeServer`, start it in the hosted service, `CreateClient()` after readiness.

## Open risks

- CI cost and flakiness of process-spawning tests on three OS (bun install time, cold boots).
- Port-zero readiness parsing: the contract is one stdout JSON line, but later stdout writes and
  stderr noise must never wedge the probe — continuous drain is mandatory.
- Windows tree-kill semantics differ by TFM (`entireProcessTree` vs `taskkill`); net472 has no
  first-class async stdout drain, so the downlevel read loop needs deadlock-proof design.
- An unattached drive controller hangs the server's prompting path: the fixture and controller
  must fail fast with bounded timeouts, never hang the suite.
- Fixed default drive ports (40900/40950) collide under parallel or concurrent-branch CI runs;
  the named-instance manifest is the mitigation and must be proven on all three OS.
