### R01 - high - streaming deserialization regression in the copied-reader union scan
- `src/OpenCode.Sdk/Internal/Serialization/UnionDiscriminatorReader.cs:84` `scan.Skip()`.
  `Utf8JsonReader.Skip()` throws `InvalidOperationException("Cannot skip tokens on partial JSON...")`
  whenever the reader's `IsFinalBlock` is false, regardless of buffered completeness. STJ's stream entry
  points (`JsonSerializer.DeserializeAsync`, `DeserializeAsyncEnumerable`, `Deserialize(Stream)`,
  PipeReader overloads) hand converters a reader whose `IsFinalBlock` mirrors the stream state, so every
  generated marked-union converter (all `*JsonConverter.cs` using `UnionDiscriminatorReader`) throws
  `JsonException` with that inner exception for known and unknown arms. `DeserializeAsyncEnumerable`
  fails even for a two-element array; `DeserializeAsync` fails when the payload is not in the final
  buffer chunk (e.g. 50 KB `IEvent[]`, 96 KB `MessageListResponseEnvelope`, `DefaultBufferSize=64`).
  The public interfaces carry `[JsonConverter]` attributes, so a consumer's own `JsonSerializerContext`
  picks the converter up. Parent emitter (`git show f306270:tools/OpenCode.Sdk.Tools/Generator/Emission/
  UnionEmitter.cs` ~line 477) used `JsonDocument.ParseValue` (TrySkip-based) -> genuine Arc 6 regression.
  SDK-internal paths (`Pipeline` frames as strings, `ResponseAdapter` spans, `OpenCodeErrorReader`
  strings) always see `IsFinalBlock=true` and are unaffected.
- Fix: `if (!scan.TrySkip()) { throw new JsonException($"The {conceptName} payload ended before '{propertyName}'."); }`
  (inside a converter STJ read-ahead guarantees the value is complete, so `TrySkip` succeeds; same pattern
  as `JsonDocument.ParseValue`). Hand-written file; no generator change needed.
- Red tests (any OS): `tests/OpenCode.Sdk.Tests/Serialization/OpenCodeJsonContextTests.cs` -
  `DeserializeAsyncEnumerable<IEvent>`/`<ISessionMessageInfo>` over a `MemoryStream` with a small
  `DefaultBufferSize` (known, unknown, and the nested fixed-marker `ISessionMessageCompaction` arm),
  `DeserializeAsync<MessageListResponseEnvelope>` of a multi-item page, and one object with trailing
  whitespace padding beyond the buffer. Fixtures go under `Fixtures/Serialization` (no inline JSON).
- Docs: state in `docs/architecture/protocol-and-generation.md` (owner of union dispatch) that the
  known-arm scan is partial-reader safe; ADR-0009 may get a one-line relay.
- Why missed: every union test deserializes a complete string/span; canon never said whether
  consumer-side stream deserialization of SDK models is supported.

### R19 - high - downlevel SSE read ignores enumeration cancellation while a read is pending (Windows)
- `src/OpenCode.Sdk/Internal/Pipeline.cs` `ExecuteStreamCoreAsync` hands the raw response stream to
  `ServerSentEventReader.ReadAsync` (`ServerSentEventReader.cs:82`
  `stream.ReadAsync(bytes.AsMemory(), cancellationToken)`). On `!NET`, Polyfill's `ReadAsync(Memory,
  ct)` forwards to `Stream.ReadAsync(byte[],int,int,ct)`. The owned downlevel transport is
  `HttpClientHandler` over `HttpWebRequest`; its response content is a `StreamContent` over a
  `WebExceptionWrapperStream : DelegatingStream` whose inner `ConnectStream` overrides only
  `Read`/`BeginRead`/`EndRead` (no `ReadAsync(ct)`), so the base `Stream.ReadAsync` checks the token once
  and then runs an uncancellable `BeginRead/EndRead`; HttpClient disposes its linked CTS after
  `ResponseHeadersRead`, so the handler's `webRequest.Abort()` registration is dead; `ConnectStream`
  applies `ReadTimeout` only to synchronous reads, so there is no ReadWriteTimeout backstop. Result: on
  .NET Framework (net472, or netstandard2.0 loaded by .NET Framework), cancelling `SubscribeAsync(token)`
  / `GetLogAsync(..., token)` while the stream is idle waits for the next byte. Modern path verified OK
  (`SocketsHttpHandler` `ContentLengthReadStream.ReadAsync` registers cancellation that disposes the
  connection). Pre-existing, not Arc 6. Evidence came from decompiling the corefx net46 build of
  `System.Net.Http.dll` shipped in the SDK test host on Linux; **verify against the inbox 4.7.2
  assembly on Windows**.
- Windows probe first (decisive): `LoopbackHttpServer` (exists in `tests/OpenCode.Sdk.Tests/Support`)
  answering `text/event-stream` with `KeepOpen`, deliver one frame, cancel the enumeration token while
  idle, measure `MoveNextAsync` latency and whether the response/connection is released.
- Fix candidates: on `#if !NET` register `cancellationToken.Register(static s => ((HttpResponseMessage)s!).Dispose(), response)`
  for the enumeration lifetime (or wrap each read in the `WaitAsync` + dispose pattern the one-shot readers
  use), and widen the `MoveNextAsync` catch so `HttpRequestException`/`IOException`/`ObjectDisposedException`
  observed while `cancellationToken.IsCancellationRequested` rethrow as `OperationCanceledException(token)`.
- Red test (Windows net472 leg, `#if NET472` or TFM-conditional): loopback `KeepOpen` stream, cancel
  mid-idle -> `OperationCanceledException` within a bound, response disposed. Note the behavior in
  `client-runtime.md` (SSE section) and ADR-0010.
- Why missed: `ExecuteStreamAsync_Should_Honor_Cancellation` pre-cancels; `BlockingStream`/
  `CancelingStream` fakes honor the token themselves; the net472 two-stream starvation test passes
  `CancellationToken.None`.

### R17 - medium - stream-open error body read with an infinite budget
- `Pipeline.cs:504` `ReadBodyAsync(response, Timeout.InfiniteTimeSpan, cancellationToken)` for the non-200
  branch of `ExecuteStreamCoreAsync`. With `ResponseHeadersRead` modern HttpClient disposes its timeout
  CTS after headers (`HttpClient.SendAsync` -> `FinishSend`), `SocketsHttpHandler` has no read timeout, so
  a 4xx/5xx answer with a stalled chunked body hangs the first `MoveNextAsync` until caller cancellation;
  the generated parameterless `SubscribeAsync()` invites `CancellationToken.None`. Arc 6 budgeted the one-
  shot path (`GetRemainingTimeout`) but left this literal with no rationale in code, canon, Q120, or handoffs.
  Probe: mock handler, `HttpClient.Timeout=100 ms`, 500 + never-completing body -> stream `MoveNextAsync`
  pending > 3 s while the one-shot shape threw `OpenCodeTransportException(TimeoutException)` at 108 ms;
  a caller token did settle it (TaskCanceledException at 300 ms, content disposed).
- Fix: capture `Stopwatch.GetTimestamp()` before `SendCoreAsync` in `ExecuteStreamCoreAsync` and pass
  `GetRemainingTimeout(requestStarted)` to the non-200 `ReadBodyAsync` (the 200 SSE body stays unbounded
  by design). Alternative if the exemption is intentional: document it in `client-runtime.md` and test
  that caller cancellation settles the blocked read.
- Red test (any OS): `PipelineStreamTests.ExecuteStreamAsync_Should_Keep_An_Error_Body_Inside_The_Transport_Timeout`
  with `BlockingContent` + small `HttpClient.Timeout` -> `OpenCodeTransportException` with `TimeoutException` inner.
- Why missed: `PipelineStreamTests` has no timeout case.

### R02 - medium - `charset=utf-7` leaks a raw `NotSupportedException` (modern TFMs)
- `ResponseEncodingPolicy.cs:64` catches only `ArgumentException` around `Encoding.GetEncoding`; on .NET 5+
  `GetEncoding("utf-7")`/codepage 65000 throws `NotSupportedException` (SYSLIB0001 switch off by default),
  and neither `ReadSuccessBodyAsync` nor `ReadBodyAsync` catch filters include it, so `OpenCodeClient`
  throws `System.NotSupportedException` on 200 and on error statuses. net472 still supports UTF-7, so the
  behavior differs by TFM. Probe through the real `Pipeline` reproduced both planes on net10.
- Fix: map `NotSupportedException` beside `ArgumentException` in `ResolveEncoding` (wrap as the same
  `InvalidOperationException("invalid charset")`) so both planes end as `OpenCodeTransportException`;
  the error plane still goes through BCL `ReadAsStringAsync`, so also add `NotSupportedException` to the
  `ReadBodyAsync` catch filter (or route the error plane through the policy, see R10/R12).
- Red tests (any OS): `PipelineTests` 200 and 401 with `charset=utf-7` -> `OpenCodeTransportException`
  on modern TFMs; on net472 assert the decoded behavior instead (TFM-conditional expectation).
- Why missed: charset tests cover only `not-an-encoding` (`ArgumentException`) and a UTF-16 BOM body.

### R10 - low - net472 success/error plane asymmetry for a quoted charset (Windows)
- Success plane (`ResponseEncodingPolicy.ResolveEncoding`, all TFMs) strips one pair of quotes before
  `Encoding.GetEncoding`, mirroring dotnet/runtime `HttpContent.ReadBufferAsString`; the error plane
  (`Pipeline.ReadBodyAsync`) calls the platform `ReadAsStringAsync`, and .NET Framework's `HttpContent`
  passes `CharSet` verbatim, so on net472 `charset="utf-8"` yields a typed envelope on success but
  `OpenCodeTransportException` on any error status. Before Arc 6 both planes failed identically. Canon
  (`client-runtime.md:46-52`, ADR-0014) says "equivalent to HttpContent string decoding" - true for the
  modern BCL algorithm only (22-case differential probe on net10: all SAME).
- Decision needed: (a) make the policy the single decoder on every TFM (error plane reads bytes ->
  `Decode` -> `RawBody = DecodedBody ?? UTF8.GetString(Utf8Body)`; this also collapses the two readers,
  see R12), or (b) word canon as "equivalent to the modern BCL algorithm; net472 error plane keeps
  Framework semantics". Either way add quoted-charset tests for both planes so the Windows net472 leg
  records real behavior.
- Why missed: no quoted-charset test anywhere; the Windows leg never saw one.

### R16 - medium (performance) - success body heap-copied twice
- `Pipeline.cs:338` `ReadAsByteArrayAsync` = `LoadIntoBufferAsync` (exact-size non-pooled array when
  Content-Length is known; pooled then reallocated when chunked) + `CreateCopy`/`ToArray`; the array is
  only handed to `adapter.AdaptSuccess(status, span)` and never retained. New ladders show the read path
  at **2.00x wire bytes at every size** (6,112 B of 19,608 B deep; 2,154,817 B for a 1 MB body with Gen2
  collections). Probe: `ByteArrayContent.ReadAsByteArrayAsync` 4,840 B/op vs `LoadIntoBufferAsync` alone
  2,616 B/op for 2,191 B.
- Follow-up (measured, not before the correctness repairs): read the content stream (`ReadAsStreamAsync`/
  `CopyToAsync`) into an SDK-owned pooled buffer while keeping the timeout/cancellation/dispose-on-cancel
  structure on both TFM families; gate on `MessageGetBenchmarks.ExecuteWithoutAdapterAsync` (expect ~1.0x
  wire) and the ownership tests. Not a contract cost (ADR-0007 RawBody applies to errors only).

### R18 - medium (performance) - SSE reader per-character walk and per-frame string
- `ServerSentEventReader.cs:89-157,197`: `Accept()` per decoded char, `StringBuilder.Append(char)`,
  `_data.ToString()` per frame, `JsonSerializer.Deserialize(string)` transcoding back to UTF-8. A
  contract-neutral stage-1 prototype (same strict decoder; `IndexOfAny('\r','\n')` over
  `characters.AsSpan(0, decoded)`; `Append(char[],int,int)` slices; CR-split/BOM flags kept) measured
  **690 -> 105 us** on the 64-large-frame parser arm and **390 -> 162 us** on 1,024 small frames with
  identical output and allocation. Stage 2 (byte-oriented reader, `ServerSentEvent.Data` as
  `ReadOnlyMemory<byte>` valid until the next `MoveNextAsync`, frame limit in bytes, strict UTF-8 via
  `Utf8.IsValid` on `NET` and the strict decoder downlevel) is a design decision because it changes
  `ServerSentEvent`, `IStreamAdapter`, and the stream-adapter emitter. Gate both on
  `ServerSentEventReaderBenchmarks` and `SessionLogStreamBenchmarks`.

## Why the tests did not catch the bugs (systemic answer)

1. **Complete-buffer bias**: every serialization test deserializes a complete string or span, so a
   reader with `IsFinalBlock=false` never entered the suite (R01). Add a standing rule: every converter
   family gets one `DeserializeAsync`/`DeserializeAsyncEnumerable` case over a small-buffer stream.
2. **Fakes that cooperate**: cancellation/timeout tests use `BlockingStream`/`CancelingStream`/
   `BlockingContent`/`TimeoutContent` doubles whose `Dispose` releases the pending read, proving the
   pipeline's control flow but not the owned transport's response streams (R19, R15). The loopback server
   exists but is used only for the net472 starvation test with `CancellationToken.None`.
3. **One-shot got the Arc 6 hardening, the stream-open plane did not get the test** (R17).
4. **Charset matrix too small**: `not-an-encoding`, UTF-16 BOM, malformed UTF-8 only (R02, R09, R10).
5. **Adapter overload drift**: Arc 6 added the span `ReadBarePayload` but the probe adapter only exposes the
   string overload (R13); the nested carrier guard was proven as emitted text, not constructed (R14).
6. **Windows-only leg sees only what is written for it**: no quoted-charset, no mid-read cancel case.
