## Appendix A — Code review prompt

> Copy from here. Self-contained: it names its own reading, scope and output format, and
> depends on no particular tooling.

You are performing an adversarial code review of a .NET SDK repository. Your job is to find
real defects. A clean result is a valid and useful outcome — do not manufacture findings to
appear thorough, and do not accept an author's stated reasoning as evidence for anything.

**Repository:** a .NET SDK for opencode's HTTP API. It is generated: a hand-written behavior
core plus a Roslyn-emission generator under `tools/`, whose committed output lives under
`src/OpenCode.Sdk`.

**Scope:** the commit range `f6a569a..b19e32d` on `master`. That range adds a Server-Sent
Events engine, converts generated union types from abstract records to interfaces, and admits
the first streaming operation.

**Read first — this repository documents the standards you must judge against, and general
C# taste does not override them:**
1. `AGENTS.md` at the repository root.
2. Every file in `docs/adr/` (0001–0012).
3. `docs/engineering/coding-style.md` and `docs/engineering/testing-style.md`.

**Then review, in this order of value:**
1. `src/OpenCode.Sdk/Internal/ServerSentEventReader.cs` and
   `src/OpenCode.Sdk/Internal/Pipeline.cs` (the streaming path) — parser edge cases, resource
   lifetime on every exit path including early abandonment of the enumeration, cancellation,
   and behavioral parity with the one-shot path beside it.
2. `tools/OpenCode.Sdk.Tools/Generator/` — the binder and emitters. Ask whether each new rule
   is derived from schema *shape* or from a name, and whether any fail-closed wall was
   widened further than the change required.
3. The committed generated output under `src/OpenCode.Sdk` — it is public API and is
   explicitly review surface in this repository.
4. `tests/` — whether the new tests would still pass if the production code were broken.

**Method.** For every candidate finding, construct the concrete input or sequence that
triggers it and trace the code by hand to the wrong outcome. Then check whether an existing
test already covers it. Discard anything you cannot demonstrate this way. Do not report style
preferences, naming opinions, or "consider adding a comment" items.

**Report** as a plain list, most severe first. For each finding give: the file and line, the
exact trigger, the traced-through wrong behavior, whether a test covers it, and which written
rule it breaks if it breaks one. End with a short list of what you examined and found sound,
so the reader knows the review's coverage.

## Appendix B — Verification prompt

> Copy from here. This is not a bug hunt. It checks whether a set of factual claims made
> during the work are actually true.

You are independently verifying factual claims made by a previous engineer about a .NET SDK
repository. Your job is **not** to find bugs and **not** to evaluate design. It is to
establish, for each claim below, whether it is true, false, or unverifiable — using the
repository and its pinned inputs as evidence.

Treat the claims as unproven. Do not reason from the author's commit messages or
documentation: those *are* the claims. Settle each one against a primary source — the pinned
specification at `spec/openapi.json`, the upstream sources under `external/opencode/`, the
code itself, or a command you run. State the exact command or file that settled it.

For each claim, report one of:
- **CONFIRMED** — with the evidence that settles it.
- **REFUTED** — with the evidence, and what the truth is instead.
- **UNVERIFIABLE HERE** — with what would be needed.

### The claims

1. In `spec/openapi.json`, 39 of the 40 branches of `Session.Event.Durable` are also direct
   branches of the 87-branch `V2Event`; the exception is `session.usage.recorded`, and
   `EventLog.Synced` is not a `V2Event` branch.
2. Every numeric single-value `enum` in that spec declares `type: number`; none declares
   `type: integer`. The count is 41.
3. Exactly 12 sites in the spec carry `anyOf[{"type":"object"},{"type":"array"}]`, and this
   shape is how Effect renders a struct with no declared fields — upstream's own generated
   client types the corresponding value as `{}`.
4. Exactly 4 sites carry an `anyOf` whose branches are all refinements of `string`, and one of
   them is the session parent filter — so collapsing that shape during ingestion rather than
   during binding would erase a sealed design (research log Q78).
5. Effect's SSE encoder writes an `event:` line only when the event name is not `"message"`,
   and an `id:` line only when an id is defined. Consequently an ordinary payload frame on
   the wire carries neither.
6. `v2.session.log` and `v2.event.subscribe` are served by different upstream code paths: the
   first through Effect's `StreamSse` encoder, the second through a raw handler that writes
   `data:` frames by hand and sends `: heartbeat` comment lines.
7. Upstream's own generated client discards the `event` field, while Effect's own parser keeps
   it and strips a leading UTF-8 byte order mark.
8. `v2.session.log` has exactly one consumer in the upstream repository, and
   `v2.event.subscribe` has many more — the durable log is a diagnostic channel, the live bus
   is the product surface.
9. Of this SDK's five target frameworks, only `netstandard2.0` and `net472` resolve
   `Microsoft.Bcl.AsyncInterfaces`; `IAsyncEnumerable<T>` is a BCL type from `net8.0` on.
10. `JsonConverterAttribute` can target an interface, and a source-generated
    `JsonSerializerContext` will deserialize both into an interface-typed member and into the
    interface directly through a converter declared that way.
11. On `netstandard2.0` and `net472`, `StringBuilder.Append(StringBuilder, int, int)` resolves
    to a Polyfill shim whose body materializes the entire source builder as a string — so a
    change made to avoid an intermediate string does not avoid it on those two targets, and
    the benchmark figures recorded in the M3 plan are `net10.0` only.
12. The conversion of generated unions from abstract records to interfaces changed no runtime
    behavior: the full test suite passes and the public API baseline is identical across all
    three .NET targets it is generated for.
13. Against `opencode2 serve` v0.0.0-next-17403, the durable session log emits only its
    `log.synced` watermark: the aggregate sequence stays at 0 across repeated session renames
    and a completed assistant turn, while `/api/event` emits normally in the same window.
    (Claim 13 needs a running server; mark it unverifiable if you cannot start one, and say
    so rather than guessing.)

Finish with a one-paragraph summary: how many claims held, which failed, and whether any
failure changes a decision recorded in `docs/adr/` or `docs/ROADMAP.md`.
