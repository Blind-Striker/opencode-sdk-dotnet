## Stopwatch and custom-infrastructure clarification

- `Stopwatch.GetTimestamp()` was already present in Arc 6 before this Windows continuation to keep
  one-shot send plus body consumption inside `HttpClient.Timeout` after `ResponseHeadersRead` returns.
  R17 applied the same remaining-budget rule to stream-open error bodies. It is timeout-budget machinery,
  not telemetry instrumentation, but it contributes to orchestration complexity.
- The committed `ResponseBodyReader` still uses BCL `ReadAsByteArrayAsync`. The ArrayPool-backed writable
  stream and disposable body lease exist only in the uncommitted R16 experiment below.
- Mature peers do own similar internals: Azure.Core centralizes buffering, network-timeout cancellation,
  live-stream disposal, and read-timeout wrapping in `ResponseBodyPolicy`; AWS SDK centralizes invocation,
  unmarshalling, and streaming-response ownership in its runtime pipeline. This supports evaluating a
  deep internal pipeline, not copying their public surface or accepting custom pooling automatically.

### What the experiment does

- `HttpContent.CopyToAsync` writes into an `ArrayPool<byte>`-backed stream. Content-Length is only an
  initial-capacity hint; a lying/unknown length grows geometrically.
- Decoding receives the actual written length so spare pool capacity cannot affect empty, BOM, UTF-8,
  malformed, or charset behavior.
- An `EncodedResponseBody` lease owns pooled UTF-8 memory only through synchronous adaptation; string
  `RawBody` remains independent.
- The destination owns the pooled array separately from the pending copy task. Timeout/cancellation can
  reclaim the array immediately even if the source task never settles; late writes fail and late faults
  are observed.
- Tracking-pool tests cover growth, spare-capacity poisoning, exact return counts, timeout reclamation,
  idempotent disposal, and use-after-dispose. The SDK test project passed 1,378/1,378 across four TFMs.

### Why it is paused

Review found one important correctness issue: if caller cancellation races a copy task faulting as
`IOException`, `HttpRequestException`, or `ObjectDisposedException`, the first catch currently maps it
to `OpenCodeTransportException` instead of honoring the canceled caller token. Minor findings: the
stream reports `CanWrite=true` after detachment/disposal, and `PooledResponseBodyBuffer` is a shallow
facade allocation added mainly to satisfy disposal/task analysis.

The experiment passes the mechanical full repository gate but is not committed and must not be treated
as the chosen runtime architecture: review still fails on the Important cancellation race. Do not patch
these three findings and commit by momentum; first decide the module shape in the clean architecture
session.

## Why work stopped

The accumulated need is broader than R16. The committed `Pipeline` currently owns:

1. options snapshot and credential validation;
2. owned handler and client construction;
3. modern connection lifetime and downlevel `ServicePoint` policy;
4. request creation, serialization, endpoint/route joining, authentication, location, and User-Agent;
5. send, redirect refusal, network failure and cancellation classification;
6. total timeout budgeting across headers and buffered body;
7. response body buffering, charset/BOM/UTF-8 policy, and ownership;
8. one-shot success/error adaptation and throw/`NoThrow`;
9. stream opening, event-stream media checks, downlevel response-dispose cancellation;
10. SSE frame reading, named failure dispatch, typed cause/payload materialization, and stream errors.

These responsibilities are coherent at the product level but too many lifecycle policies now share one
orchestration implementation. R16 can be made locally correct, yet doing so without deciding the larger
module shape risks adding another layer that a later refactor immediately replaces.

## M4 product target and boundaries

M4 remains `OpenCodeServer.StartAsync` in `OpenCode.Sdk`, hand-written over
`System.Diagnostics.Process` per ADR-0001. It starts and monitors the known `opencode2 serve` executable,
drains stdout/stderr without deadlock, discovers readiness, owns graceful then forceful shutdown, and is
accepted against a real process on Linux, Windows, and macOS.

Do not let the runtime refactor silently expand M4 into M5 breadth, #53 walls, package/release work,
telemetry/retry/hooks implementation, spec refresh, MCP work, binary download, background service
discovery, or public transport extensibility unless the architecture design explicitly reopens one of
those decisions with evidence.
