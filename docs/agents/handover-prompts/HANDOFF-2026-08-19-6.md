## Exact Next Increment - Arc 4 Paginator

Arc 4 starts with a short public API decision before source mutation:

1. Survey current primary .NET pagination APIs and compare an `AsyncPageable`-like sequence of pages
   with a plain `IAsyncEnumerable<T>` item sequence plus explicit per-page access. Evaluate caller
   ergonomics, cancellation, error timing, page metadata access, allocation, and extend-only
   compatibility. Bring a recommendation to the maintainer; do not code through an undecided shape.
2. Build only on the existing `ListRequest`, `ListCursor`, `ListOrder`, generated
   `MessageListRequest`, `MessageListResponse`, and `SessionClient.ListMessagesAsync` seams. Do not
   create a parallel pagination vocabulary or endpoint-specific transport path.
3. Derive traversal only from the pin: `order` shapes the first page; returned items retain that
   order across pages; opaque `cursor.next` and `cursor.previous` move through the ordered timeline;
   `limit` remains the pinned string representation. Never decode, increment, compare, or otherwise
   infer cursor internals.
4. Do not resurrect #28's local order+cursor refusal. ADR-0013/#54 removed that prose-derived runtime
   rule; the current contract test deliberately sends both. The declared `InvalidCursorError`
   remains on the typed API-error path.
5. After the shape is approved, land one bounded vertical implementation with generated/public API
   review, deterministic multi-page request/response evidence, cancellation and typed-error timing,
   source-generation/AOT compatibility where the shape reaches serialization, Extensions/public
   examples as applicable, and a precise live demonstration if the real server can produce more
   than one message page without synthetic semantics.
