## The headline: the 2.0 branch is an ancestor, not the destination

Doc 09 treated the `2.0` branch spec as where upstream is going. The branch's own history says
the opposite — it is where upstream **came from**:

- The `2.0` branch head is `7a6ce05d` ("2.0 exploration (#22335)"), committed **2026-04-13**.
  PR #22335 was **merged into `dev` that same day**, and the branch has been frozen since: it is
  0 ahead / **4244 behind** `dev` (compare API, 2026-08-08), with zero Actions runs on record
  (90-day retention caveat).
- The timestamped beta builds do **not** come from the `2.0` branch. `beta.yml` on `dev` runs
  hourly and merges team-labeled PRs into a `beta` branch on top of `dev` (`script/beta.ts`);
  `publish.yml` publishes on pushes to `ci`/`dev`/`beta`/`snapshot-*`. npm dist-tags at
  retrieval: `latest: 1.18.15`, `dev: 0.0.0-dev-202608080352`, `beta: 0.0.0-beta-202608081801`.
- The v2 machinery **postdates** the 2.0 exploration: `packages/httpapi-codegen` first landed
  on `dev` 2026-06-25 (#33445), and the protocol contract was extracted 2026-06-25 (#33708,
  "refactor(protocol): extract server contracts") — two months **after** the 2.0 branch froze.
  The 2.0 branch itself has no `httpapi` code at all (Hono server,
  `packages/opencode/src/server/instance/*`).

So the 112-operation document at `packages/sdk/openapi.json` on the `2.0` branch (OpenAPI
3.1.1, 94 paths, 163 schemas — matching doc 09's counts exactly) is the **April 2026 ancestor**
of today's surface, not the next major's surface. Cross-checking it against the pinned
v1.18.15 spec proves the descent: **110 of its 112 operationIds exist verbatim in the v1.18
root-mounted block** (what doc 09 calls "legacy"); the other two are
`experimental.workspace.adaptor.list` (today spelled `…adapter.list`) and
`global.sync-event.subscribe` (removed on `dev` since). The root block has meanwhile grown 17
ops the April surface lacked (list below). The mapping in this document therefore reads
"the v2 surface vs its ancestor", not "the v2 surface vs its future".

## Where each spec block actually comes from

On `dev`, both blocks of the pinned spec are generated from one composed Effect HttpApi
(`packages/opencode/src/server/routes/instance/httpapi/api.ts`):

- `OpenCodeHttpApi = RootHttpApi + EventApi + InstanceHttpApi + ServerApi + PtyConnectApi`.
- `RootHttpApi`/`InstanceHttpApi` are built from `httpapi/groups/*` (21 files) and declare the
  **unprefixed dotted identifiers** — `groups/global.ts` annotates `global.health`,
  `global.config.get`, … verbatim. These generate the 127-op root block. The "legacy" block is
  not old code: it is a live Effect HttpApi contract whose names descend from the April
  surface.
- `ServerApi = makeApi(...)` imports from **`@opencode-ai/protocol`** (`packages/protocol/`,
  18 groups: agent, command, credential, event, fs, health, integration, location, message,
  model, permission, project-copy, provider, pty, question, reference, session, skill — exactly
  the `v2.*` families). This is the source of the 61-op `/api` block.

Corrections to doc 09 this implies: the `httpapi/groups/` contract is **not** "the 2.0-shaped
contract that the v2 block projects" — it generates the *root* block; the v2 block comes from
the separate, newer `packages/protocol`. And "developed on a separate 2.0 branch and shipped
as timestamped beta builds" conflates a dormant April branch with the dev-based beta channel.
Doc 09's raw numbers all reproduced (15/61 verbatim; 97/112 outside the v2-set); its
*direction* was inverted — `v2.health.get` → `global.health` is not a rename that will happen,
it is a rename that already happened, the other way around.

## Systematic differences, v2 (newer) vs ancestor/root (older)

The per-op noise is five systematic conventions the protocol surface introduced; the full
table below only notes drift *beyond* these:

1. **Response envelopes:** ancestor returns bare schemas (`Session`, `Pty[]`); v2 wraps
   everything in `{data}` or `{data, location}`.
2. **Location addressing:** ancestor ops take `directory`/`workspace` query params; v2 takes
   `location` (deep-object `location[directory]`/`location[workspace]` where split).
3. **Schema naming:** v2 mints `*V2*` names (`SessionV2Info`, `AgentV2Info`, `V2Event`,
   `PermissionV2Request`) for the clean ancestor names (`Session`, `Agent`, `Event`, …).
4. **Session scoping:** ancestor keeps permission/question ops unscoped
   (`/permission/{requestID}/reply`); v2 nests them under `/session/{sessionID}/…` and splits
   list ops per scope.
5. **Pagination:** ancestor uses `before`/`limit`-style params with bare arrays; v2 uses
   `cursor` params with `{cursor, data}` envelopes.

## pty.connect and WebSockets (doc 09 UNVERIFIED item, resolved)

- The 2.0-branch spec **does** contain `pty.connect` (GET `/pty/{ptyID}/connect`, 1 of the pty
  group's 6 ops), described verbatim as "Establish a WebSocket connection to interact with a
  pseudo-terminal (PTY) session in real-time", modeled as a plain GET returning `boolean`.
  The server route is a real WebSocket upgrade
  (`packages/opencode/src/server/instance/pty.ts` on the branch: `hono/ws` `upgradeWebSocket`).
- Upstream's own generated client does **not** exclude it: the branch's hey-api-generated JS
  SDK (`packages/sdk/js/src/gen/sdk.gen.ts`) emits `Pty.connect()` as an ordinary HTTP GET with
  no WebSocket handling — a faithful rendering of the spec's fiction. The ROADMAP's "upstream's
  own codegen excludes them" does not hold for this artifact.
- On `dev`/v1.18.15 the op also exists on both surfaces (`v2.pty.connect` with a
  `connect-token` handshake added; `httpapi/websocket-tracker.ts` exists server-side). So in
  every spec we may generate from, `pty.connect` appears as a **fake plain GET whose real
  protocol is a WebSocket upgrade** — the generator can emit it mechanically, but a working
  client needs hand-written WebSocket support or an explicit exclusion.

## Consequences for the API design session

1. **Naming: do not treat the 112 names as a rename destination.** They are the ancestor's
   names, alive today as the root block. The newest naming layer upstream produced is the
   protocol package's — i.e. the prefix-stripped `v2.*` names our ADR-0005 policy already
   adopts. The genealogy correction *supports* the locked naming decision and removes the
   "absorb the 2.0 rename wave" pressure doc 09 implied: there is no verified rename wave to
   absorb, because no authoritative next-major spec exists. (2026-08-13: one now exists — the
   active `v2` branch publishes `packages/protocol/openapi.json`, a continuation of the same
   protocol family with `v2.`-prefixed operationIds; see `15-opencode-v2-platform.md`.)
2. **ADR-0005's deletion premise needs re-grounding, not reversal.** "At opencode 2.0 the
   legacy area is deleted" was partly argued from the 2.0-branch spec; that evidence is void.
   The live signals still point the same way (TUI migrating to `sdk.client.v2.*`, deprecation
   markers, protocol extraction) but the shape and date of the next major are now UNVERIFIED.
   (2026-08-13: resolved — ADR-0005 revised in place: the SDK targets the v2 protocol surface
   only; the legacy surface is never built.)
3. **The capability gap is precisely enumerated.** The 78-op list is what the MCP server and
   any full-capability consumer must take from the legacy sub-surface today (`tui.*` 13,
   `mcp.*` 8, session-editing 16, config/auth/project/vcs/find/lsp/etc.), plus the 17
   post-April root additions (`sync.*`, `vcs.*`, `pty.shells`, …).
4. **Cross-surface signature asymmetry is systematic.** Even the 15 same-name ops differ in
   envelope, location addressing, pagination, and schema naming — and `session.prompt` differs
   in its whole interaction model (async admission + `wait` vs sync response). The public API
   must not promise that a modern call and its legacy namesake are shape-compatible.
5. **The durable session stream is protocol-only.** `v2.session.events`/`v2.session.history` +
   `SessionDurableEvent` (the spec's single `oneOf`) have no ancestor/root counterpart — the
   locked SSE-resume design (`after` cursor) rides the newest, least-proven part of the
   surface. (2026-08-13: the trio was since dropped on the `v2` branch in favor of
   `v2.session.log` (`after`/`follow`) and cursor-paged `v2.message.list`; the M3 stream
   design is re-derived against that surface — research doc 15.)
6. **`pty.connect` needs an explicit decision:** exclude from generation, or generate the
   fake GET and pair it with hand-written WebSocket support (upstream ships the fake GET).
